## Issue 1 — kiosk showed "Templates: 0" for a student who had enrolled

### Root cause (not the enrollment, not the roster, not the consent)

The template was **perfectly valid**. `students` → `face_enrolled=true`,
`face_consent=granted`, profile `active`, `deleted_at` null; `face_templates` →
`status=granted`, `dimension=128`, `samples_count=5`, `ciphertext=256 B`, `iv=12 B`,
`auth_tag=16 B`.

The failure was in the envelope decoder. `decryptDescriptor()` normalised the `\x`
prefix for `ciphertext` only:

```ts
const ctRaw = row.ciphertext.startsWith("\\x") ? Buffer.from(row.ciphertext.slice(2), "hex")
                                               : Buffer.from(row.ciphertext, "base64");
const decipher = crypto.createDecipheriv("aes-256-gcm", key(), Buffer.from(row.iv, "base64"));
decipher.setAuthTag(Buffer.from(tag, "base64"));            // ← hex string treated as base64
```

PostgREST returns `bytea` as a `\x<hex>` literal. A 12-byte IV arrives as 24 hex chars
and a 16-byte tag as 32 hex chars, so base64-decoding produced **14-byte and 20-byte**
buffers and every decryption threw:

```
TypeError: Invalid authentication tag length: 20
```

Live proof: six `kiosk.template_decrypt_failed` audit rows for student
`365e70f7-…` at 18:25–18:31, and the three `unknown_face` attempts that followed
carried `confidence = 0.000` with high liveness (0.68, 0.88) — the signature of an
empty matcher set.

### Fix

`src/lib/server/templates.ts` now has one `byteaToBuffer(value, field, expectedLength)`
used for ciphertext, IV and tag. It accepts `Buffer`/`Uint8Array`, `\x`-hex, bare hex,
base64 and JSON byte arrays; it filters candidates by the **expected length** (256/12/16)
so the parse is deterministic rather than heuristic, and it refuses ambiguous or
malformed input with a precise message instead of an opaque crypto error.

`src/app/api/kiosk/templates/route.ts` now reports failures instead of swallowing them
(`template_failures`) and audits the real error string — student ids only, never key
material.

### Kiosk synchronization is now self-explaining

`fetchTemplates()` returns a `sync` report (`enrolled_students`, `templates_received`,
`templates_loaded`, `excluded[]`, `problems[]`). The kiosk panel shows `Templates 2 / 3`
plus, e.g., `1 × template could not be decrypted on the server`, so "zero" can never
again look the same as "nobody enrolled".

### Liveness — the second, independent defect

Production attempts showed genuine users failing at **0.596** and **0.217** while a
static photo scored 0.15. Reading the scorer explained it:

| Old behaviour | Consequence |
| --- | --- |
| `livenessMetrics` demanded `samples.length >= 3` | with 2 frames every metric became 0 |
| no timestamp handling | a blink from 10 s ago still counted; frames were unordered |
| blink = EAR span over the whole window | sampling at **420 ms** skips a ~150 ms blink entirely, then reports "No blink detected" |
| `stable` gave **+0.15 to a frozen photo** | a still image banked free points |
| turn needed only `yawSpan ≥ 0.045` | a held head pose counted as motion; no return to centre required |

That also explains the observed 0.596: iris micro-motion + the frozen-photo bonus landed
just under the 0.60 threshold.

Fixes (`src/lib/face/engine.ts`, `src/app/kiosk/page.tsx`):

- evidence is **timestamped** and clipped to a 2.6 s window, so stale blinks are ignored;
- blink is an open→closed→open **class** with an observability check: at a median
  sample gap > 260 ms the kiosk says *"could not sample your eyes fast enough"* and asks
  for a re-scan instead of falsely accusing the user;
- turn requires a **reversal** (excursion either side of the mean), so a held tilt fails;
- nod is a real depth cue (face width vs height, i.e. foreshortening), not a scale-up;
- the frozen-photo bonus is **removed** — a still frame now scores exactly 0;
- the challenge must be passed on its own evidence class; the remaining 0.5 is bounded
  micro-motion;
- kiosk sampling changed to **180 ms** (120 ms during the blink challenge) and the
  challenge runs 4.2 s with visible progress.

Thresholds in `gym_settings` are untouched (recognition 0.48, liveness 0.60).

### Two bugs found *while* validating the fix

Writing the adversarial cases exposed two flaws in my first rewrite, both now fixed and
both locked into the suite:

1. **The evidence window was shorter than the challenge.** A 2.6 s window inside a 4.2 s
   challenge discarded a blink performed in the first second — the user was shown "No
   blink detected" for a blink they really did. Window is now 4.5 s and must stay above
   `CHALLENGE_MS`.
2. **Jitter was being scored as motion.** Spans were measured min→max, so ±4 px of
   detector noise on a *static photograph* accumulated 0.5 — just under the threshold.
   Every span is now the 10th–90th percentile, and the challenge thresholds were raised
   above the measured noise floor (they had been set *below* it).

That second point forced a re-weighting. With noise no longer inflating motion, a genuine
blink — which moves the head very little — fell to 0.565. The fix was not to lower the
bar but to weight evidence honestly: **passing the mandatory challenge is now 0.75** and
motion the remaining 0.25, because a photograph cannot blink or turn out and back while a
photo in a shaky hand still has some motion.

## Issue 2 — `attendance_records` HTTP 400

The query asked for two embeds to the same person:

```
profiles:profiles!attendance_records_student_id_fkey(...)
students:students!attendance_records_student_id_fkey(...)
```

Live FK catalog: `attendance_records_student_id_fkey` references **students**, not
profiles. PostgREST therefore cannot resolve the first embed and rejects the whole
request (`PGRST200`, HTTP 400).

Fix: one path — `students:students!attendance_records_student_id_fkey(..., profiles:profiles!students_id_fkey(full_name,email))`,
because `students_id_fkey → profiles(id)` is the only student↔profile link.

**The same bug was on the live monitor** (`profiles!attendance_records_student_id_fkey`),
which means "currently inside" could never have rendered — fixed identically.

## Issue 3 — `session_bookings` HTTP 400

`session_bookings.student_id → students.id`, so `profiles:profiles(full_name)` on a
booking is unresolvable (`PGRST200`, HTTP 400). Fixed to
`students:students!session_bookings_student_id_fkey(enrollment_id, profiles:profiles!students_id_fkey(full_name))`,
with a `unwrap()` helper because PostgREST returns to-one embeds as object *or* array.

## Issue 4 — `/api/admin/retention` HTTP 500

Two defects, one fatal:

1. **Fatal.** `retention_status()` is `SECURITY DEFINER` and begins
   `IF NOT is_super_admin() THEN RAISE EXCEPTION 'FORBIDDEN'` — it authorises from
   `auth.uid()`. The route called it with the **service-role** client, which has no JWT,
   so every load returned HTTP 500. Reproduced live: `set local role service_role;
   select retention_status();` → `42501 FORBIDDEN`. The same call with a super-admin JWT
   returns the full payload. Fixed by calling it with `ctx.db` (the caller's session).
2. **Silent.** The cron probe used `.schema("cron").from("job")`; the API roles hold
   `SELECT` on `cron.job` but **no `USAGE` on schema `cron`** (`has_schema_privilege` =
   false), and its error was never inspected, so `cron` was always `[]`.

Fix: `retention_cron_jobs()` (migration 013, super-admin/trusted-server only, returns
job name/schedule/active and nothing else) plus error checks on all four queries. The
page also claimed the job ran "1st of every month, 02:30 IST" while the real schedule is
`0 21 28-31 * *` (last day, 21:00 IST) — it now displays the schedule read from
`pg_cron`.

Six-month policy untouched; `retention_enabled=false`, `retention_armed=false`; no
cleanup executed.

## What is still NOT verified — read this

- **No browser and no camera exist in this environment.** Every camera path
  (`getUserMedia`, model loading in the browser, the live challenge loop, realtime
  subscriptions) remains **unverified**. The liveness work is validated against
  anatomically-shaped synthetic landmark sequences and the real scorer; it is **not** a
  real-camera test. Someone must stand in front of the USB camera at GYM DESKTOP 1.
- **The PostgREST 400s are fixed by relationship analysis, not by replaying the query.**
  There is no egress to PostgREST here and no local Postgres, so the corrected embeds
  were validated against the live FK catalog (`students_id_fkey`, `session_bookings_*`,
  `trainers_id_fkey`) rather than executed. Confirmation requires loading the attendance,
  monitor and sessions pages in a browser once deployed.
- **Liveness is still a heuristic**, not ISO/IEC 30107-3 certified. The rules are
  stricter than before (a printed photo now scores 0.000).
- **Cron has still never fired unattended** (next: 2026-11-30 21:00 IST); retention has
  only ever run inside rolled-back transactions.
- The kiosk's `template_failures` list is intentionally just a count per reason — it
  never reveals which student failed or why, to keep the kiosk view non-identifying.
